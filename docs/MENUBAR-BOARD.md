> 目标：把「Hub 重写每个工具的菜单」改成「完整呈现每个工具原本的菜单栏界面」，并让用户决定每个工具的菜单栏落点

## 0. 一句话结论

现在的 Hub 是**「摘要卡 + 重绘菜单」**：它拿工具注册的菜单树，重新画成 2 个 chip，剩下全塞进 `...` 的 NSMenu。
你要的是**「完整菜单 + 落点管理」**：每个工具的菜单原样可看、可点，并且由你决定它在系统菜单栏还是 Hub 看板里。

这两件事在 macOS 上有一个躲不掉的物理限制，先说清楚，方案才站得住。

---

## 1. 硬约束：跨进程没有「嵌入视图」这回事

macOS **没有公开 API** 能把 A 进程的 NSView / NSPopover 塞进 B 进程的窗口。
`NSRemoteView` 是私有 API（Apple 自用于 XPC service），不能用。

所以「完整显示工具原本的界面」只有三种落地形态，保真度与代价完全不同：

| 形态 | 长什么样 | 保真度 | 可交互 | 代价 |
|---|---|---|---|---|
| **① 真身弹出** | 点开某工具 → Hub 面板让位 → 该工具在菜单栏下方弹出**它自己那份 NSMenu 对象** | 100% | ✅ 原生 | 工具要加一个 `onPopupRequest` 回调；进程需 activate；面板要让位，有轻微闪烁 |
| **② 镜像渲染** | Hub 面板内就地展开菜单树，用系统原生菜单样式绘 | 结构 100%，视觉 Hub 化 | ✅ 可搜索、可键盘 | 工具要维护菜单映射（**容易漏项**，见 §2）；自定义视图项（滑块/图表）表达不了 |
| **③ 截图镜像** | 工具把 popover 截图像素级推给 Hub，Hub 贴图 + 转发点击 | 像素 100% | ⚠️ 静态，Hover 子菜单失效 | 需要屏幕录制权限；每次交互都要重建；脆弱 |

**我的建议：②为主、①为辅、③不做。** 理由在 §5。

## 2. 现状诊断（有实锤）

拿 A-Sweep 举例，这是它自己 `ASweepMain.swift:116-125` 构建的**原生菜单**：

```
打开 A-Sweep
暂停监控 / 继续监控      ← 动态标题
──────────────
磁盘分析
操作历史                 ← 注册时漏了
设置…
──────────────
退出 A-Sweep             ← 注册时漏了
```

而它注册给 Hub 的（`ASweepMain.swift:292-298`）只有 5 项，且 `暂停监控` 被改写成了 `菜单栏监控` 勾选项。
卡片上你实际看到的：**「打开 A-Sweep」「磁盘分析」两个 chip**，其余全在 `...` 里。

三个问题全暴露了：
1. **两份菜单各写各的** → 必然漏项、必然漂移
2. **Hub 有"摘要"的决定权** → 它挑前 2 项当 chip，替你决定了什么重要
3. **落点不可选** → 只有「在 / 不在」，没法说"这个留菜单栏、那个收进看板"

另：截图里 A-Kit 自己显示「未接入」——Hub 没向自己注册，这是个独立小缺口，顺手修。

## 3. 新模型：三个正交维度

把「菜单栏托管」拆成三个互不干扰的维度，配置项从 1 个开关变成 3 个字段。

### 维度 A · Slot（这个工具的菜单栏落在哪）

| Slot | 含义 | 谁来建 NSStatusItem |
|---|---|---|
| `bar` | 用自己的图标留在系统菜单栏（现状，Hub 不碰） | 工具自己 |
| `hubbar` | **Hub 代持**：Hub 在自己的状态栏区域画这个工具的图标 | Hub |
| `board` | 收进 Hub 面板，系统菜单栏不占位 | 无 |
| `hidden` | 哪都不显示 | 无 |

`hubbar` 这一档是关键：**只有 Hub 代持，图标的顺序、分组、间距才真正由 Hub 掌控**。
`bar` 模式下顺序由各 app 启动顺序决定，Hub 管不了（这是系统限制，不是设计选择）。

### 维度 B · Render（在 Hub 里怎么呈现它的菜单）

| Render | 说明 |
|---|---|
| `native` | 真身：工具弹自己那份 NSMenu（对应 §1 形态①） |
| `mirror` | 镜像：Hub 按菜单树原生渲染（对应形态②） |
| `status` | 只显示一行状态，无菜单 |

### 维度 C · Board（面板里的排布）

| Board | 说明 |
|---|---|
| `expanded` | 常驻展开完整菜单（小工具适合） |
| `collapsed` | 折叠成一行，点开才展开 |
| `focus` | 同一时刻只展开一个，其余折叠（工具多时防爆炸） |

组合示例：A-Sweep = `hubbar + native`（图标留菜单栏，点了弹它自己的真菜单）；
NetPulse = `board + mirror`（不占菜单栏，在面板里常驻展开网速曲线那一套）。

## 4. 功能清单

优先级：**P0 = 这一版必须做**（否则诉求没解决）、**P1 = 下一版**、**P2 = 可选**。

### A 组 · 协议与数据（地基，全部 P0）

| # | 功能 | 说明 | 验收标准 |
|---|---|---|---|
| F1 | **菜单同源** | SDK 新增 `AKMenuSource` 协议：工具用**同一份数据**同时生成 `NSMenu` 和 `[AKMenuItem]`，禁止两份手写 | A-Sweep 改造后，原生菜单与 Hub 菜单项数一致（8 = 8） |
| F2 | **协议 v2 字段** | `AKToolInfo` 增 `render`、`slot`、`iconPNG(base64)`、`menuVersion`、`dynamicMenu` | 老工具不传也能注册（默认值兜底） |
| F3 | **菜单树能力补全** | `AKMenuItem` 增 `iconName`、`toolTip`、`badge`、`isDestructive`；子菜单支持任意深度 | 深度 3 的子菜单正确渲染 |
| F4 | **动态菜单推送** | 工具菜单变化时主动 `update(menu:)`；A-Sweep 的「暂停/继续」必须走这条 | 点「暂停监控」后，菜单文字在同一次交互内变成「继续监控」 |
| F5 | **自指项处理** | 工具菜单里的「退出 X」「关于 X」在聚合视图里自动降级到该工具的 `...` 二级菜单，不混进主列表 | Hub 主列表不出现「退出 A-Sweep」，`...` 里可找到 |

### B 组 · 落点管理（你的诉求二）

| # | 功能 | 优先级 | 说明 |
|---|---|---|---|
| F6 | **每个工具一个「落点」选择器** | P0 | 四选一：系统菜单栏（自持）/ 系统菜单栏（Hub 代持）/ Hub 看板 / 隐藏。控制台工具行、面板卡片 `...` 菜单各一个入口 |
| F7 | **控制台「菜单栏编排」页** | P0 | 拖拽排序、按组显示、一键「全部收进看板」/「全部放回菜单栏」。现在 `AKLayout.groups` 的语义从"面板分组"升级为"菜单栏分组" |
| F8 | **Hub 代持图标（hubbar）** | P0 | Hub 创建 statusItem 画工具图标；点击行为可配：弹真身菜单 / 展开看板卡片 / 执行默认动作 |
| F9 | **代持图标的分组与间距** | P1 | 同组图标窄间距、组间分隔线；顺序完全由 Hub 掌控 |
| F10 | **未接入工具如实标注** | P0 | 明确显示「未接入 · 无法代管」，并给引导（收敛现有 `thirdPartyHiding`）。**不假装能管** |
| F11 | **一键回滚到出厂** | P1 | 所有工具恢复「各自持有图标」，Hub 只当控制台 |

### C 组 · 完整菜单呈现（你的诉求一）

| # | 功能 | 优先级 | 说明 |
|---|---|---|---|
| F12 | **卡片改版：完整菜单区** | P0 | 取消「2 个 chip」的摘要逻辑。折叠态一行状态，展开态**完整菜单树**就地渲染：分隔线、勾选、禁用、子菜单、图标全保留 |
| F13 | **真身模式（native）** | P0 | 点开 → Hub 面板让位 → 工具原样弹出自己的菜单。面板关闭后自动恢复 |

| F16 | **菜单搜索** | P1 | 输入即跨所有工具过滤菜单项，回车执行。这是镜像模式相对原生菜单的唯一优势，值得做 |

## 5. 三条技术路线对比（要你选）

| | 路线 A：全镜像 | 路线 B：全真身 | 路线 C：双轨（推荐） |
|---|---|---|---|
| **面板内体验** | ✅ 就地展开、可搜索、可键盘 | ⚠️ 面板要让位，菜单弹在外面 | ✅ 按工具选 |
| **保真度** | 结构 100%，视觉 Hub 化 | 100% 原样 | 各自最优 |
| **工具改造量** | 中：菜单同源（本来就该做） | 中：加 `onPopupRequest` + 留 NSMenu 引用 | 大：两种都要支持 |
| **漏项风险** | 有（靠 F1 同源根治） | 无（就是它自己那份） | 无 |
| **跨进程风险** | 无（全在 Hub 进程内） | 有：activate 抢焦点、App Nap 下响应慢、面板闪烁 | 有，但可降级到镜像 |
| **能否搜索** | ✅ | ❌ | ✅（镜像项） |
| **视觉一致性** | ✅ | ❌ 每个工具长得不一样 | ⚠️ 混杂 |

**我的推荐：C，默认镜像、真身作为「原样打开」的出口。**

理由：
- 镜像全在 Hub 进程内，零跨进程风险，是唯一能稳定做到「面板里就地看全」的路
- 真身是唯一 100% 原样的路，但不能作为唯一路径（弹菜单要激活进程，面板必然要让位，做不到"嵌在面板里"）
- 所以每张卡给两个入口：**展开**（镜像，就地看）/ **原样打开**（真身，弹它自己的）
- 用户第一次用默认镜像；觉得某个工具镜像不对，切真身

如果你更看重"必须是原样"，那就走 B，代价是放弃面板内展开和搜索，退化成"Hub 只是入口，菜单还是各弹各的"——那 Hub 的面板就基本只剩启动器作用了。

## 6. 需要你拍板（5 个）

**Q1 · 主路线**：A 全镜像 / B 全真身 / **C 双轨（我推荐）**

**Q2 · `hubbar`（Hub 代持系统菜单栏图标）做不做？**
- 做：顺序、分组、间距完全可控，这才是"管理哪个显示在系统菜单栏"的完整答案
- 不做：只能靠工具自己建图标，顺序由启动顺序决定，Hub 管不了
- 我的建议：**做**，但排在 P0 后半段（F8），因为它依赖图标数据（F22）

**Q3 · 面板默认排布**：`expanded` 常驻展开 / `collapsed` 折叠 / **`focus` 单开（我推荐）**
工具一多，全部常驻展开面板会变得很长。focus 模式能保证「看一个的时候它是完整的」。

**Q4 · 工具的「退出 / 关于」怎么办？**
- 收进 `...` 二级菜单（我推荐，主列表干净）
- 或：原样保留在列表里（100% 忠实，但 Hub 里出现"退出 A-Sweep"容易误点）

**Q5 · 协议破坏性变更**
`AKMenuItem` 加字段是兼容的，但 `render`/`slot` 是新语义。要不要给 v0.4 的老工具做兼容层（不传字段 → 按 `board + mirror + collapsed` 处理）？
我建议**做兼容层**，否则 A-Sweep、NetPulse 都得同步改版才能不出错。

## 7. 建议落地顺序（拍板后）

1. **协议 v2 + 菜单同源**（F1-F5）：先让"两份菜单"变成"一份"，这是后面一切的地基
2. **A-Sweep 试点改造**：验证 8 项全对、动态标题实时翻转
3. **面板卡片改版 + 镜像渲染**（F12/F14/F19）：诉求一落地
4. **落点选择器 + 编排页**（F6/F7/F10）：诉求二落地，先不做 hubbar
5. **真身模式**（F13）：补"原样打开"出口
6. **hubbar 代持**（F8/F9/F22）：最后做，因为它最容易被系统更新影响

## 8. 明确不做

- **截图镜像（形态③）**：要屏幕录制权限、静态、脆弱，收益不抵成本
- **AX API 去动别人的 statusItem**：DESIGN.md 已否掉，继续否掉
- **替第三方未接入工具"假装完整显示"**：只能显示「未接入」，不编造
